Review Ready Field Guide

The pre-PR pass. Run it when development on a branch is finished and before the pull request exists. It builds a clean series beside your branch, has it reviewed, and then moves the branch onto it, so the PR that opens is small, obvious, and would be ACKed by a Linux kernel maintainer in 2000.

The problem

Generation got fast. Review did not.

A coding agent returns a task-sized change for a task-sized prompt. It does not decompose the work, respect a diff budget, or stop at the edge of what you asked. The result lands on the one step that never got faster.

Before agents, the cost of writing code was the throttle, and it enforced good behaviour for free. A person produced a couple hundred good lines a day, so a large change meant weeks on a branch, and nobody tolerated that much drift from main. Writing and understanding were the same act, so you could only write as much as you could hold in your head. Laziness kept diffs lean: no test for a trivial getter, no docstring on every helper, no guard against impossible states. Reuse was cheaper than writing, so you looked for the existing utility first.

Every one of those brakes is now released, and one thing is worse than merely unchanged. Clean code used to be a proxy for a careful author. Reviewers leaned on that proxy without knowing it. A model produces textbook style whether or not the logic is right, so polish no longer signals correctness, and uniform polish hides where the risk is: human code has texture, and the hard part looks hard. Errors moved from syntax, which every linter catches, to semantics, which none of them do.

What this skill does about it. It puts the brakes back, but as mechanism rather than social pressure. The rules are old. The enforcement is a script that refuses to build a series whose commits do not each stand alone, and a reviewer that never shares the author's context.

Getting started

Say what you want in your own words.

There is nothing to install and no command to memorise. The skill is already on disk; describing the situation is what invokes it.

Any of these will reach it, and the wording picks the mode:

I've finished this branch. Clean it up before I open the PR.
This branch is 4,000 lines and I only asked for a dedupe.
Would a kernel maintainer ACK this?
Implement the spec the kernel way, as a patch series.
Read the whole repo and tell me if it's clean. Restructure it.

It works on a repository under git, because everything it produces is a patch series and everything it promises is checked by building one. On a tree with no version control there is nothing to bisect and no way to revert, so that is the first thing to fix.

Your branch moves once, at the end. The whole pass, which on a large branch is long, happens beside it: the series is built on a detached HEAD in a private worktree and kept in a ref, no branch is created or deleted, and your checkout is never touched. If the session dies half way, you are exactly where you started. Only after the maintainer's ACK does one command move the branch onto the series, and it writes the undo to disk before it prints it.

feature/dedupe-loader now holds the series (4920739007 -> 0d6e9c644e).

Your branch as you left it: 4920739007a8... (refs/review-ready/original/feature/dedupe-loader)

Put it back, from any branch:

    git -C /path/to/repo checkout -B feature/dedupe-loader refs/review-ready/original/feature/dedupe-loader

written to .review-ready/feature_dedupe-loader/UNDO.md

A rewrite you cannot undo from what you were told is a rewrite you did not consent to. An earlier version printed an undo that only worked from the branch itself; pasted from main a day later, it would have hard-reset main.

Work files land in .review-ready/<branch>/, one directory per branch so a second PR never inherits the first one's files, and excluded through git's own exclude file rather than .gitignore, since editing a tracked file would itself be an unrequested change. Untracked files of yours (.env, data, notes) are never touched, and notebooks or data files the series drops are kept in your working directory as untracked copies.

Four modes

The mode follows from what you are holding.

A branch that exists, a spec that does not, a PR you are judging, or a whole tree nobody has justified.

pre-pr default
"clean up my branch", "before I open the PR"

Prunes the branch to what the problem needs, refactors what stays, splits it into small bisectable patches, writes the messages and the PR description, reviews as the maintainer, fixes every NAK, and only then moves the branch onto the series, with the undo written to disk.

write
"implement this spec the kernel way"

The same output, but the series is planned before any code exists. Each patch is written, committed and checked one at a time. A patch heading past its budget is split rather than finished.

review
"would this pass?", "ACK or NAK"

A verdict and nothing else. Changes nothing in the tree, not even the work directory. A missing problem statement is the first NAK; one gets reconstructed from the diff and labelled as reconstructed.

audit
"read all the code", "restructure it"

Maps the whole repo, judges it, proposes a tree whose layout explains itself, and refactors what fails behind characterization tests. Output is still a series.

Say which mode was picked. "Make my branch pass review" is pre-pr, not review: the ask is to fix it, not to judge it.

Doctrine

Eleven ground rules, and the reason each exists.

Every one of them protects a human reviewer with finite attention, which is exactly the constraint a coding agent has no model of.

One logical change per patchA bug fix, a cleanup, an API change and a new user of that API are four patches. A reviewer verifies one claim at a time.
Never mix movement with modificationNobody can see a one-line logic change inside a 300-line reformat, and that is precisely where the bug will be.

Doctrine

The ten things that get cut.

Each is a habit of generated code, and each is a NAK with a specific objection behind it. Walk every hunk and ask whether the problem statement needs it.

  1. Whitespace, reformatting, quote style and import reordering on lines not otherwise changed.
  2. Drive-by renames and refactors. "While I was here" is a second patch or a deferred item.
  3. Abstractions with one user: a class with one method, a base class with one implementation, a config object for two parameters, a factory for one product.
  4. Comments and docstrings that restate the signature, carry history, narrate the line below, or outweigh the code they sit on; and type hints added to code this patch does not otherwise change.
  5. Defensive code for states that cannot occur, try/except "just in case", and anything that swallows an error.
  6. Duplicates of something the tree already has. Search first, reuse, and name what was reused in the message.
  7. Tests that assert the implementation, tests of trivial code, and mocks of the thing under test.
  8. Generated files, unrelated lockfile churn, notebook outputs and data files.
  9. Debug prints, debug logging, TODOs and commented-out code.
  10. Options, flags and config knobs nobody asked for.

What survives still gets the taste pass. A function over two screens or three levels deep is flattened with guard clauses or split at its seam. A magic number gets a name. A special case is removed by picking the representation that makes it disappear, which is Linus's linked-list rule: the code that needs no branch for the first element is the code that got the data structure right.

Re-run the audit afterwards. If the reviewable line count did not fall substantially, the prune was too gentle. A typical agent-written branch loses half or more here.

Doctrine

The message explains why. The diff already says what.

It is the only part of a patch that survives into git log, git blame, and the bisect result someone reads at two in the morning five years from now. Write for that reader.

loader: drop duplicate (ticker, date) rows, keeping the last

The vendor file repeats a row whenever a close is restated, so
load_prices() returns two rows for the same ticker and date and every
downstream mean is weighted toward restated days. Last week's report
showed AAPL with 23 trading days in a 21-day month.

Keep the last occurrence, since a restatement supersedes the original.
Using file order rather than a timestamp is deliberate: the vendor file
carries no restatement time, so file order is the only ordering there is.

The report still sums n_rows over the rows it is given, which is now the
deduplicated set; no change needed there.

Test: tests/test_loader.py::test_duplicate_dates_keep_last fails on the
parent commit and passes here.

Signed-off-by: Your Name <you@example.com>

Subject area: imperative summary near 60 characters. Body wrapped at 72, because that is what every tool the reviewer has assumes.

What the shape is doing

  • Problem before solution. The reader must be able to disagree with the diagnosis before they see the cure. A message opening with the fix skipped the part review exists to check.
  • Present tense about the tree, not past tense about you. "The loader keeps duplicate rows", never "I noticed" or "Updated the loader".
  • Name the alternative you rejected. One sentence. It stops the reviewer suggesting it and shows the choice was made rather than defaulted into.
  • Say what is deliberately out of scope when a reader would expect it, which saves a round trip.
  • Say how you tested. "Ran the tests" is weak. "Fails on the parent, passes here" is a claim the reviewer can check, and the builder now warns when a body never says it.
  • A prep patch ends with "No functional change." That sentence is a promise, and the reviewer verifies it by looking for any changed test.
  • Never mention the tool. The reviewer is reviewing a change and the person submitting it.
Doctrine

A comment says what the code is for and how to use it.

That is the whole brief. Everything else is a cost the reader pays on every visit, and most of it is a cost that grows: prose about code is checked by nothing, so it drifts away from the code silently and then misleads with the authority of a comment.

The test is blunt. A ten-line function does not need thirty lines of prose above it. Someone who reads more comment than code to reach the code has been charged twice for one function.

The two things that earn their place

  • What this is and how to call it. One sentence at the top of a module, class or public function. A reader scanning a directory listing should be able to place every file from its first line.
  • The fact the code cannot state. Units, ranges, what a missing value means, the invariant a loop maintains, why the obvious alternative is wrong, the trap that cost someone a day. This is the only kind that gets more valuable over time, because it is the only kind holding something the code does not already hold.
def sessions_between(start, end):
    """Trading sessions in [start, end), in the exchange's timezone."""
    # The exchange calendar is authoritative; a naive weekday count is wrong
    # around holidays, which is what the half-day table below is for.
    return _calendar.sessions_in_range(start, end)

Three lines of prose on three lines of code, and both earn it: the docstring says what you get and that the interval is half-open, the comment says why the obvious implementation is wrong.

What is not history. A date is not history when the date is the subject: a trading calendar, a fixture, a table of holidays, a regulatory deadline. "Historical" is not history when it describes the data or the behaviour, as in a historical replay. The auditor requires a change-of-code verb or explicit changelog framing before calling a date history, and judging by hand uses the same test. Deleting a comment that documents a domain fact is a worse outcome than leaving one that documents a commit.

On a real trading repository, the first version of this rule produced nine findings and every one was a market-calendar fact. Tightening it removed all nine and kept the rest.

The budget

A function is flagged when its docstring and comments together outweigh its body and amount to at least eight lines; when a body of three lines or fewer carries a docstring of six or more; and when a docstring runs past twelve lines over a body under twenty. A module docstring past thirty lines is a document that wants to be a document.

These find candidates, they do not pass verdicts. A parser whose grammar needs explaining, a numerical routine with a derivation, a public interface with real usage examples: each can legitimately run long. What cannot is a wrapper, an accessor, a dataclass, or a five-line function doing one obvious thing.

Fixing them is its own patch

Removing a comment changes no behaviour, so it lands as a patch saying "No functional change.", verified by seeing that no test moved. Group by file, not by kind: one patch per file reads as a decision someone made about that file, while twenty patches split by category read as a sweep, and a sweep is what nobody reviews. Never mix a comment patch with a logic patch, because a deleted comment beside a changed condition is the classic place a real change hides.

Doctrine

Risks a clean diff can still carry.

Style checks pass on all of these. Each is wrong in a way that reads as correct, which is why generated code is where they hide best. Seventy-two line detectors, ten syntax-tree checks and one check over file names find where to start looking; none of them is a verdict.

The truncation test

The check that ships with any feature patch, and it needs no model and no backtest: a point-in-time feature for row t is unchanged when every row after t is deleted. A z-score over the whole history fails it, because the mean includes next year. A lagged expanding window passes. Most look-ahead bugs fail this one test.

Pandas patterns only fire in pandas files

A round( or a .values in a module that never touches a frame is not a finding, and reporting it teaches the reader to skip the section. Detectors that need pandas or a model library switch off in files with neither. Context-dependent checks use the syntax tree instead of a line pattern: the first version flagged time.sleep as "blocking call inside async def" twelve times in a repository with no async code at all.

A finding is never fixed silently. A confirmed risk in code the branch wrote is fixed in the patch that introduces that code. A risk in code that was already there is its own patch if small and certain, and otherwise an open question in the PR description. It is never folded into an unrelated patch.

Doctrine

Behaviour is not only the lines in the diff.

Config keys, environment variables, defaults, sample data, import order and the clock all change what code does without appearing as logic. The kernel calls these Kconfig options, module parameters and boot arguments, and requires a new one to arrive in its own documented patch, defaulting to off.

So the problem statement carries two things the diff cannot show: the call chain from the entry point down to the changed line, and every switch that controls the behaviour along with the position each is in today. Thirty-three detectors sweep the added lines for them, grouped by kind, plus three rules no line pattern can express.

KindWhat hides there
configEnvironment reads, settings imports, feature flags, and CLI flags carrying a default.
defaultsParameter defaults, dict.get with a non-None fallback, getattr fallbacks, silent or, NaN coerced away.
sequenceModule-level calls, registration decorators, cache and retry wrappers, cron and callback registration, mutated globals, dynamic import.
environmentWall-clock reads, timezone and locale, dates parsed with an inferred format, unseeded randomness, worker counts, version gates.
testsA test that patches a module constant, fakes an environment variable, or asserts a call instead of a result.

The three commit-level rules

  • Config or data changed in the same commit as code. The reviewer cannot tell whether the code is right for the old data, the new, or neither.
  • A config key nothing reads. A dead switch tells a reader the behaviour is configurable when it is not, and whoever sets it sees nothing happen.
  • An environment variable read but never set. Whatever it defaults to is the real, undocumented behaviour.

Dark-launch ordering. A patch that flips a switch adds the new path guarded off, so the patch changes nothing. Both positions get a test. Then the default flips in its own patch whose entire diff is the flip, so reverting that one commit is the rollback. Its message states the old behaviour, the new behaviour, why now, and that reverting restores the old. Removing the old path is a later series.

Doctrine

Characterize before you refactor.

This is the gate, and it is what separates refactoring from rewriting.

A refactor changes the code and not the behaviour. If nothing pins the behaviour, you cannot know you did that, so the claim in the commit message is false. A function with no test is a function whose behaviour nobody wrote down; rewriting it does not preserve behaviour, it replaces behaviour with your reading of the code, and the suite still passes because there was nothing there.

i

Write a characterization test first, in its own patch. Not a test of what the function should do: a test of what it does now, including the parts you think are wrong. Feed it a real input, record the actual output, assert that.

ii

Run it against the unchanged code. It must pass. A characterization test that fails on the parent is not characterizing anything, it is a bug report; land it as one, with the fix.

iii

Refactor in a separate patch, and do not touch the test. The test file being unchanged is the reviewer's proof behaviour was preserved. If the refactor forces a test edit, either the test was testing the implementation or the behaviour changed. Both are findings; neither is a refactor.

iv

A behaviour change is never a refactor. A genuine bug gets its own patch, its own failing-then-passing test, a message saying what was wrong, and it is not described as a cleanup.

Where behaviour is genuinely unpinnable in reasonable time, a function that calls a network, a clock and a database in one body, the honest first patch is the seam that makes it testable: pass the dependency in rather than reaching for it. That patch is itself a refactor, so its characterization test sits at the nearest testable boundary one level up, and the message says so.

Running it

The eight steps of the pre-PR pass.

They are numbered because they are genuinely sequential: each one narrows what the next has to decide.

00

Establish the ground

First, what do the tests open? A suite that reaches the operator's database or the network is not run blind. Then one command, audit_diff.py, produces the report everything else works from, and its Ground section decides whether the pass can start: the fork point and the target (fetch moves origin/main and never main, so the fresher one is used); a test merge when the target has moved, because a same-line conflict cannot be resolved by anything written at the fork point and is yours to settle on your branch before hours are spent; whether the branch has more than one author; whether it is already published.

The test command never runs in your checkout: it runs in an export, and later in a private worktree, of tracked files only. The interpreter is named by absolute path, and on a src/ layout the path is PYTHONPATH=src, relative. An absolute one points at your checkout, and every check would then pass or fail on the original code whatever the series contains. An import probe catches that. "Did not run", "timed out" and "vacuous" (green with nothing run, or everything skipped) are reported as themselves, never as pass or fail.

Then the focus map, before any of the diff is read: for every function the branch adds or changes, the call chain up from it, each caller with the line that calls it, and what it calls, led by the additions to act on (used once, never called, called only by tests, already in the tree). It is the neighbourhood of the diff, not the whole repo, and it is for reading: the pass still changes only what the branch wrote.

On a big branch the diff is not read top to bottom: the audit and the focus map first, the noise classes never, then files by reviewable lines.

01

State the problem, the switches, and the data contract

One paragraph on what is wrong in the tree today, how it shows, and what the change does about it. Then the call chain, the switches, the data contract, who outside the repository consumes this code, and one question most reviews skip: is the diagnosis right? The failing case is walked through the old code. A fix at the reader for bad rows a writer produces is a symptom patch, however well it is split.

A problem statement written from a diff always matches the diff, so it counts only once you agree with it. Your request stating what you asked for is that agreement; otherwise you are shown the paragraph and asked once. A question nobody can answer becomes an open question in the PR, never a guess.

02

Prune

Edits do not happen on the branch. The version of each file a patch should contain is written under the work directory's overlays/, mirroring the repo path, and the builder assembles them. Overlays are whole files, so a fix made to patch 2's overlay must be carried into patch 3's; the builder reports a later overlay that drops what an earlier patch added.

Then the ten categories above. Four of them remove behaviour, not noise: the except that gets dropped may have been absorbing a real vendor failure. So every dropped hunk gets a line in deferred.md, tagged noise (by class and count) or behaviour (one line each). You decide later; nothing is decided silently.

03

Rewrite what stays to the minimum

Pruning removes hunks the problem does not need. It cannot touch the bigger waste in agent code: hunks the problem does need, written at two to four times the length. So each surviving file is rewritten from its contract, starting from the base version rather than trimming the draft, because trimming keeps every layer the agent invented. Every case the draft handled and the rewrite does not is either put back in its shortest form or recorded as deferred behaviour. The target is half the branch's lines or less, and the builder checks it (step 05). Shape, algorithm, language contracts, data, security and tests are fixed in the same pass. Scope is lines inside functions the branch's diff already changes, and files it adds. Everything else is a deferred item, and the builder enforces it: a file the branch never touched is refused unless the plan gives its reason. A refactor that changes what a caller sees, such as a None return made to raise, is a behaviour change to code you ran and the tool did not, and it is reported to you as one even when it is right.

04

Split into a series, and size the PR

Preparatory patches first, each saying "No functional change." and changing no assertion. Then the behaviour change with its tests in the same patch. Then new users of a new interface: a function lands with its first caller, because code nothing calls is dead on main. Then the cleanups.

Two budgets, because there are two risks. Edits to existing code can break everyone who depends on it: about 200 reviewable lines, rarely more than six patches. New self-contained files with their tests, imported by nothing until the last patch, can break nobody: up to about 500 lines. This is how large features actually landed in 2000: a few small justified patches to shared code, then the new files.

Past that, and only after the rewrite, a stack. A stack of long PRs is the same review in more sittings, and the size gate measures the whole series, so it is no way around the rewrite. One plan builds the whole series and a stack field cuts it into branches, each mergeable alone, your branch the top. The first PR is opened alone; the next when it merges. Seven dependent PRs in one morning is a patch bomb, and it got the same answer then: silence.

05

Write the messages, then build

One file per patch, with no sign-off line and no --- line: the builder commits the file verbatim and refuses both. Then the build, which never moves your branch: patch by patch on a detached HEAD in a private worktree outside the repo, the check after every commit from a cleaned tree, the result kept in a ref. When the target has moved, the series is rebased onto it and checked at every commit there too.

Then the size gate: per file, the lines your branch changed against the lines the series changes, counting non-blank lines and ignoring whitespace, so that neither dropping churn nor deleting blank lines can pass. The series may keep at most half, in total and in every file the branch changed by twenty lines or more. A file that truly cannot shrink is listed in the plan with its reason, which also goes in the PR description. A failed gate fails the build, and landing refuses the series. Branches under a hundred such lines are not gated, because a small fix cannot be halved.

Two more things it prints are read line by line. The residual: what your branch had that the series does not, which must equal the deferred list plus the refactors, so a dropped line nobody accounts for is work you lost. And your branch's original tests run against the rebuilt code: the per-patch check ran the pruned suite, so this is the only place a behaviour that only a pruned test covered can show.

06

Write the PR description

Under forty lines, and it stands alone: the reviewer cannot see deferred.md, so the one-line reasons are the whole deferred list. It says what was run end to end. It carries no "changes since" block: a version is a posting a human received, and rounds of the tool's own review are drafts.

07

The maintainer pass

A stranger with the problem statement, the patches, the PR description, the deferred list, the residual, the size table and the tree. For every behaviour patch the failing case is walked through the old code, to confirm the diagnosis, and through the new code, to confirm the fix, and both walks are written down. For the largest patch the reviewer sketches the shorter version they would accept; if it is clearly shorter and does the same job, that is a NAK. Fix every NAK, rebuild with the same plan, review again. Three rounds is the cap.

08

Run it, land it, hand it back

You ran the original branch; nobody has run this code. Where an entry point runs offline it is run at your original tip and at the series and the outputs are compared; otherwise the hand-back opens by telling you to run it before you sign. A defence.md is written: the three questions a maintainer would most likely ask of each patch, answered with file and line, the source of every fact in every message, and every place the refactor changed code you wrote.

Then one command lands the series and writes UNDO.md. You are asked first only when the branch has more than one author or is published and shared. The hand-back is about a dozen lines and includes one that did not exist before the reviews: "Behaviour that differs from your branch: …", each item on a line, or "none". Nothing is pushed unless asked.

The email test. Before delivering, ask one question of each patch. Could a maintainer in 2000, reading this in a text email with no IDE, no CI and no ticket, understand what it does, why, and whether it is right? If the answer for any patch is no, the series is not done.

Running it

Audit mode: a whole tree, not one diff.

Clean mode starts from a change someone wrote. Audit mode starts from a repository nobody has justified: read all of it, work out how it is wired, judge it, and change what fails.

The authority is real. Two things keep it safe. The output is still a patch series, because authority over the code is not authority over the reviewer's attention. And nothing gets refactored before its behaviour is pinned.

Reading the map before judging

Run repo_map.py, then read its report in this order, because each answer narrows the next:

  1. Entry points. Everything reachable starts here. A module reachable from no entry point and no test is a candidate for deletion, not for refactoring.
  2. The module table. Any row whose purpose reads defines ... has no docstring, so an outsider cannot place it without reading it. Cheapest finding to fix.
  3. Layers and cycles. A cycle means two modules are really one. Decide which way the dependency should point first, because the answer moves code.
  4. Hot spots. Churn times fan-in is where a defect costs most. A tidy module nobody imports and nobody changes can wait forever.
  5. Unresolved calls. The dead and untested lists are conservative by exactly that much, and the report says so rather than claiming certainty.

Then read the code from the entry points down and trace one complete path end to end before forming an opinion. An audit that never followed a request from entry to storage is a style review in costume.

A layout that explains itself

The target: someone who has never seen the repo opens it, reads the top-level listing, and can say what the system does and where to look. That is a property of layout and naming, not documentation.

  • Group by role, not by kind. ingest/, storage/, domain/, cli/ says what the code does. helpers/, models/, services/ says only what shape it is, which the reader could already see.
  • Depth follows dependency. Modules importing nothing else sit at the bottom, entry points at the top, and the import graph reads as a stack.
  • One sentence at the top of every module, saying what it is for and who calls it. Highest value per line in most trees, and it is "No functional change."
  • No catch-all package. utils/ accumulates whatever had no home, which makes it the one package nobody can predict.
  • Tests mirror the tree. A reader looking for a module's tests should not have to search.

The move lands as pure renames: git mv only, one patch per coherent group, each saying "No functional change." git diff -M shows a rename as a rename, so a 400-line move stays a one-screen review. The split that follows a move is a later patch, so its reviewer gets a real diff instead of a file appearing from nowhere.

Order of the series

Docstrings, then verified deletions, then characterization tests, then pure moves, then splits of oversized modules, then internal refactors, then bug fixes, then anything that changes behaviour. Each stage is separately reviewable and separately revertable.

Stop at a size someone will review. An audit that produces forty patches has produced a backlog, not a series. Land the first coherent group, get it merged, and let the rest be the next series. Say so in the cover letter, with a count of what remains.

What full authority does not license

  • Changing behaviour silently. Any behaviour change is called out in its own patch and in the cover letter, whatever the audit thinks of the old behaviour.
  • One large commit.
  • Refactoring what nothing pins. Characterize first, or leave it and say why.
  • Rewriting to taste where the tree has a settled convention. A consistent tree that differs from your preference is not a defect, and PEP 8 says so itself.
  • Touching what the objective does not reach: generated files, vendored code, an excluded subsystem.
Running it

The maintainer pass, and why it is a stranger.

The reviewer gets the problem statement, the patches as email, the PR description, the deferred list, the residual, the checklist, and the tree to read. Not the plan, not the conversation, not the reasoning that produced the series.

The tree matters because a real maintainer objects mostly to what is not in the diff: "you broke the other caller", "we already have that", "this backs out last week's fix". Three lines of context per hunk cannot answer those. So for every behaviour patch the reviewer takes the failing case from the message, walks it through the new code by hand, and writes the walk in the verdict; and finds every caller of a changed signature with grep rather than inferring it. Form is not correctness: a beautifully described patch with an off-by-one is a NAK, and only the walk finds it. An ACK with no trace under it is not an ACK.

It runs as a fresh subagent wherever one is available, because a reviewer who shares the author's context rationalises the author's choices. That is not a theoretical risk. In one validated run the pass caught a defect the author had introduced minutes earlier: flattening a guard to notional <= 0 is not the inverse of notional > 0 when the value is NaN, so a NaN-priced row would have gone from dropped to counted inside a patch that promised "No functional change".

Eight scripts, all read-only until the landing.

repo_map.py — read a whole repo and report how it is wired

python3 $S/repo_map.py --repo PATH [--src DIR ...] [--md FILE] [--json FILE] [--top N]

Answers what a maintainer asks before touching an unfamiliar tree. Reports the layout, what each module is for and which layer it sits in, entry points, import cycles, hot spots by churn times fan-in, functions over the 48-line or 3-level budget, untested public functions, probably-dead definitions, config keys nothing reads, and the calls it could not resolve.

It also reports the Python floor the tree declares, so "is X | Y legal here" stops being a guess, and it knows which annotations actually run: under from __future__ import annotations an X | None hint is not reported, while an alias or an isinstance argument is. A file the running interpreter cannot parse is listed at the top of the report, because every absence the map claims is blind to it; duplicates by name and by shape; repo modules imported inside functions, which usually hides a cycle; risk patterns, with inventory-style hits aggregated per file, so "CREATE TABLE in four modules" is the finding rather than twenty-four lines; and tests that assert nothing.

Whether a function is pinned by a test comes in three honest tiers: called directly by a test, reachable from one through other code, or merely sharing a name with some identifier in a test, which proves nothing. The earlier bare-name match had called five functions in a real tree "tested" on that last basis, and that list feeds the characterization gate.

Call resolution is a documented heuristic, not a type checker. It counts value references and identifier-shaped strings, not just call syntax, so a function passed to sort(key=) or a thread pool is not called dead. On a real 7,760-line repository it found three dead functions with no false positives.

build_series.py — build the series beside the branch, then land it

python3 $S/build_series.py PLAN.json            # build: never moves your branch
python3 $S/build_series.py PLAN.json --land     # the one moment it does
python3 $S/build_series.py --self-test          # 31 situations in scratch repos

Two acts, on purpose. Build commits every patch on a detached HEAD in a private worktree, runs the check after each commit, and records the result at refs/review-ready/series/<branch>. It creates no branch and deletes none. An earlier version used a scratch branch, and an adversarial review showed that one plausible plan value made it delete the owner's branch, reflog included, before any backup existed. Land moves the branch once, after the review, and writes UNDO.md first.

refs/review-ready/original/<branch> is your branch as you left it, written when the first build starts. Every review round takes its whole files, and measures its residual, from that ref, so round three is still compared with your code and not with round two. If you commit on the branch afterwards, the builder stops and asks rather than guessing, and keeps the older original.

The gates. Each one exists because an adversarial reader produced a green build that was wrong:

the base is the fork point
Whole files from a branch carry its view of every line. Built on a main that had moved, a one-line patch also deleted a guard someone else had added, and the tool certified "residual: none". The series is now built where the branch forked and rebased onto the target, checked at every commit there. A local main behind origin/main is refused: fetch never moves it.
the check tests this tree
The import probe runs with the check's own environment. On a src/ layout an absolute PYTHONPATH pointed every check at the owner's checkout, and a deliberately wrong overlay passed. Relative, it fails as it should.
a check that ran
Exit 126 or 127 is "did not run"; a hung suite is "timed out"; zero tests, or every test skipped, is "vacuous". None of them is a pass, and the owner's own pattern, tests that skip when the database is absent, used to be one.
fails before and passes after
expect_fail_before must fail on the parent's code and pass with the patch. A test name that does not exist, or a missing runner, "fails on the parent" too. The builder also says whether the parent failed by assertion or by error.
a compile floor
Every changed Python file compiles, even in a repository with no tests. A plan with no check at all must say why.
scope
A file the branch never touched is refused unless the plan gives its reason. A pre-PR pass cleans what the branch wrote; the rest is audit mode.
overlays that undo each other
Overlays are whole files, so a review fix made in patch 1's overlay was silently reverted by patch 2's, and the build certified it. A later overlay that drops lines an earlier patch added is now reported.
your tests, their code
The per-patch check runs the pruned suite. The branch's original test files are run once against the rebuilt code, and each failure must be a deferred feature's test or a change made on purpose.
the message file
A Signed-off-by line or a --- line in a message is refused: the first certifies code you have not read, the second lands in history for ever on a pushed branch.

Landing refuses tracked edits it would overwrite, a branch whose code changed since the build, and a branch checked out in another worktree. It leaves untracked files alone, keeps an overlay's executable bit, keeps pruned notebooks and data files in your working directory as untracked copies, creates the stack branches, and records the authors and the upstream so the hand-back can say what a force-push would do to colleagues.

The residual is written as git diff <your branch as you left it> <the series>: a minus line is something your branch had and the series does not. It must equal deferred.md plus the refactors, line for line.

Evidence

How it was built, and what each round found.

A skill that tells an agent to distrust green checks has no business trusting its own. The loop that produced this one: write it, run it on fixtures with known defects, have readers attack it with evidence, keep a log of every sentence that cost the executor time, fix, repeat.

The two kinds of evidence, and why both are needed

An eval asks whether an agent following the skill produces a good series, and it is graded by script rather than by reading, against a fixture whose defects were planted on purpose. It is the only honest answer to "does this work". But it cannot find what the skill lets through: a rule that is silently unsafe passes every eval, because the eval never puts the tool in the situation where it loses your work.

So the second kind: adversarial review. Readers with different lenses — a maintainer of the year 2000, an agent executing the text literally, the owner's staff engineer — are asked to find what would make the skill fail, told that praise is not wanted, and required to produce a quoted sentence with a line number or the output of a command they ran. They work in scratch repositories and may break anything. About fifty substantiated findings came out of two rounds, and every one was reproduced independently before a line was changed.

Evidence

What it does not do.

Stated here because an audit claiming complete knowledge of a tree it inferred from an abstract syntax tree is making a claim it cannot support.

  • Call resolution is a heuristic. Every dead-code and untested claim is conservative by the count of unresolved calls, which the report prints. Verify each deletion by hand: grep the whole tree including non-Python files, check whether the package exports it, and remember that "nothing in this tree calls it" is not "nobody calls it" when the tree is a library.
  • Dynamic dispatch is invisible. A name built at runtime, a plugin discovered by entry point, a template variable, a database column mapped by name.
  • The dead-key scan finds keys never mentioned, not the commoner case of a key parsed into a config object whose field nothing later reads.
  • Python only. The taste rules generalise; the scripts do not.
  • It cannot judge whether the problem statement is right. If the spec is wrong, the series will be a clean implementation of the wrong thing.
  • The maintainer pass is a model reading patches. It is a strictly better reviewer than the author, because it lacks the author's context. It is not a domain expert who knows your data.
  • Nobody has run the rebuilt series but the tests. Where an entry point runs offline it is run at your original tip and at the series and the outputs compared; otherwise the hand-back says so in its first line, and the first real execution is yours.
  • A rebase conflict with the target is yours. When the target changed the same lines, nothing written at the fork point can resolve it, and the tool stops rather than guess which side wins.

The rules here are not new. They are Documentation/CodingStyle and SubmittingPatches as they stood around 2000, which were written for exactly the constraint a coding agent ignores: one human reviewer, with finite attention, who has to say yes. What changed is that enforcement moved from social pressure on an author who wrote every line, into an instruction file and a script, because the author did not write the code.
